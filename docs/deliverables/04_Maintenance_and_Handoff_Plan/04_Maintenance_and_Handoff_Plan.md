## บทที่ 1: ข้อตกลงระดับการให้บริการและเป้าหมายความต่อเนื่อง (SLA & Business Continuity)

### 1.1 ข้อตกลงระดับการให้บริการ (Service Level Agreement - SLA)
เพื่อสนับสนุนการปฏิบัติราชการและการประเมินผลการฝึกงานได้อย่างราบรื่น กำหนดระดับการให้บริการดังนี้:

| ดัชนีชี้วัด (Metric) | เกณฑ์เป้าหมาย (Target) | วิธีการวัดผลและการตรวจสอบ |
| :--- | :--- | :--- |
| **ความพร้อมใช้งานของระบบ (Availability)** | $\ge 99.5\%$ ในเวลาทำการราชการ (07:30 - 18:30 น.) | บันทึก Uptime Monitor ผ่านเซิร์ฟเวอร์ |
| **เวลาในการตอบสนอง (Response Time)** | $< 1.5$ วินาที สำหรับหน้าจอทั่วไป และ $< 4.0$ วินาที สำหรับคำขอ AI Polish | วัดผลเฉลี่ยจาก Application Access Log |
| **เวลาในการเริ่มแก้ไขปัญหาฉุกเฉิน (Severity 1)** | ภายใน 30 นาทีหลังได้รับแจ้ง (ระบบหยุดทำงานสิ้นเชิง) | บันทึก Incident Ticket ของทีมไอที |
| **เวลาในการแก้ไขปัญหาระดับปกติ (Severity 3)** | ภายใน 4 ชั่วโมงทำการ (ฟังก์ชันบางอย่างแสดงผลผิดพลาด) | ส่งมอบชุดแก้ไข (Hotfix) ภายในวันทำการถัดไป |

### 1.2 เป้าหมายการกู้คืนระบบ (RPO & RTO Objectives)
- **Recovery Point Objective (RPO) $\le 1$ ชั่วโมง:** หากระบบเซิร์ฟเวอร์หลักเสียหาย ข้อมูลการบันทึกงานจะสูญหายย้อนหลังไม่เกิน 1 ชั่วโมง โดยอาศัยระบบ Write-Ahead Logging (WAL) และ Snapshot สำรอง
- **Recovery Time Objective (RTO) $\le 2$ ชั่วโมง:** ระบบต้องสามารถกู้คืนกลับมาให้บริการแก่ผู้ใช้งานตามปกติได้ภายในระยะเวลาไม่เกิน 2 ชั่วโมง นับตั้งแต่เริ่มกระบวนการกู้ภัยพิบัติ

## บทที่ 2: แผนการสำรองข้อมูลและการกู้คืนระบบ (Backup & Disaster Recovery Plan)

### 2.1 กลยุทธ์การสำรองข้อมูล
1. **การสำรองข้อมูลรายชั่วโมง (Hourly WAL Snapshot):** ฐานข้อมูล SQLite ในโหมด WAL จะบันทึกทรานแซกชันลงไฟล์ `ojt_logbook.db-wal` อย่างต่อเนื่อง
2. **การสำรองข้อมูลประจำวัน (Daily Automated Backup):** สคริปต์ Cron Job ทำงานทุกเวลา 01:00 น. ของทุกวัน:
   ```bash
   # สำรองข้อมูล SQLite แบบ Online Backup (ไม่ขัดจังหวะการใช้งาน)
   sqlite3 ojt_logbook.db ".backup 'backups/ojt_backup_$(date +%Y%m%d_%H%M%S).db'"
   # บีบอัดไฟล์และหมุนเวียนเก็บไว้ 30 วัน
   gzip backups/*.db
   find backups/ -name "*.db.gz" -mtime +30 -delete
   ```
3. **การจัดเก็บบันทึกประวัติ (Audit Log Mirroring):** ไฟล์ `logs/pdpa_audit.jsonl` จะถูกสำเนาไปยังโฟลเดอร์จัดเก็บข้อมูลถาวรภายนอก (Off-site Cloud Storage หรือ Google Drive) ทุกสัปดาห์

### 2.2 ขั้นตอนปฏิบัติการกู้คืนฐานข้อมูลเมื่อเกิดภัยพิบัติ (Step-by-Step Restoration)
กรณีไฟล์ฐานข้อมูลหลักเสียหายหรือเซิร์ฟเวอร์ล่ม:
1. หยุดการทำงานของ Service ชั่วคราว:
   ```bash
   kill $(lsof -t -i:8000)
   ```
2. เปลี่ยนชื่อไฟล์เดิมที่มีปัญหาเพื่อเก็บเป็นหลักฐานการตรวจสอบ:
   ```bash
   mv ojt_logbook.db ojt_logbook_corrupted_$(date +%s).db
   ```
3. คลายการบีบอัดไฟล์สำรองล่าสุดและคัดลอกมาแทนที่:
   ```bash
   gunzip -c backups/ojt_backup_latest.db.gz > ojt_logbook.db
   ```
4. ตรวจสอบความสมบูรณ์ของโครงสร้างข้อมูล (Database Integrity Check):
   ```bash
   sqlite3 ojt_logbook.db "PRAGMA integrity_check;"
   # ผลลัพธ์ต้องแสดงคำว่า "ok"
   ```
5. รันเซิร์ฟเวอร์ใหม่และทดสอบการเข้าถึงหน้าเว็บ:
   ```bash
   python run_server.py
   ```

### 2.3 การสำรองข้อมูลสำหรับระบบทางเลือก Serverless (Google Sheets)
สำหรับหน่วยงานที่ใช้ระบบ Tier 2 (Google Sheets Backend):
- Google Drive มีระบบ **Version History (ประวัติเวอร์ชัน)** บันทึกทุกการแก้ไขย้อนหลังโดยอัตโนมัติ
- ผู้ดูแลระบบสามารถคลิกเมนู **ไฟล์ $\rightarrow$ ประวัติเวอร์ชัน $\rightarrow$ ดูประวัติเวอร์ชัน** เพื่อย้อนข้อมูลกลับไปยังจุดเวลาใดก็ได้ในอดีตทันที 100% โดยไม่ต้องพิมพ์คำสั่งใดๆ

## บทที่ 3: คู่มือการแก้ไขปัญหาเบื้องต้นและคู่มือปฏิบัติการ (Troubleshooting Runbook)

### 3.1 กรณีเกิดข้อผิดพลาดจาก Gemini API (HTTP 429 Quota Exceeded)
- **อาการ:** ผู้ใช้งานกดปุ่ม "AI Polish" แล้วหน้าจอแสดงข้อความเตือน หรือเกิดความล่าช้า
- **สาเหตุ:** มีการยิงคำขอถี่เกินโควตา Free Tier ของ Google AI Studio (เกิน 15 คำขอ/นาที)
- **แนวทางแก้ไข:**
  1. ระบบของเรารองรับ **Fallback Pipeline** โดยจะสลับโมเดลไปยัง `gemini-1.5-flash-8b` โดยอัตโนมัติ
  2. หากยังติดโควตา ให้สลับ API Key สำรองในไฟล์ `.env`:
     ```bash
     GEMINI_API_KEY=secondary_backup_key_here
     ```
  3. ผู้ใช้งานยังคงสามารถบันทึกข้อความแบบพิมพ์เอง (Manual Entry) ได้ตามปกติโดยระบบไม่บล็อกการบันทึกกิจกรรม

### 3.2 กรณีไฟล์ฐานข้อมูลล็อกตัว (Database Locked)
- **อาการ:** ระบบแจ้งเตือน `sqlite3.OperationalError: database is locked`
- **สาเหตุ:** มี Process ค้างที่ยังไม่ปล่อย Connection หรือไฟล์ `.db-shm` / `.db-wal` ค้าง
- **แนวทางแก้ไข:**
  1. ตรวจสอบ Process ที่ถือไฟล์อยู่:
     ```bash
     lsof ojt_logbook.db
     ```
  2. ปิด Process นั้น หรือรีสตาร์ตแอปพลิเคชัน
  3. ตรวจสอบให้แน่ใจว่าได้เปิดโหมด WAL ในโค้ด:
     ```sql
     PRAGMA journal_mode=WAL;
     PRAGMA busy_timeout=5000;
     ```

### 3.3 กรณีปัญหาพอร์ตชนกัน (Port 8000 Conflict)
- **อาการ:** รันเซิร์ฟเวอร์แล้วขึ้น `OSError: [Errno 48] Address already in use`
- **แนวทางแก้ไข:**
  ```bash
  # ตรวจสอบว่าโปรแกรมใดใช้งานพอร์ต 8000
  lsof -i :8000
  # ปิดโปรแกรมที่ค้างอยู่
  kill -9 <PID_NUMBER>
  # หรือเปลี่ยนพอร์ตในไฟล์ .env เป็น PORT=8080
  ```

## บทที่ 4: แผนการบริหารการเปลี่ยนแปลงและการอัปเกรดระบบ (Change Management & Upgrades)

### 4.1 นโยบายการกำหนดเวอร์ชันซอฟต์แวร์ (Semantic Versioning 2.0.0)
การอัปเดตระบบจะใช้รูปแบบ `MAJOR.MINOR.PATCH` เช่น `v1.0.0`:
- **PATCH (เช่น 1.0.1):** การแก้ไขข้อผิดพลาดเล็กน้อย (Bug Fixes), การปรับปรุงคำบรรยาย หรือการอัปเดต Regex PDPA
- **MINOR (เช่น 1.1.0):** การเพิ่มฟังก์ชันงานใหม่ที่เข้ากันได้กับระบบเดิม (Backward-Compatible) เช่น การเพิ่มรายงานรูปแบบใหม่
- **MAJOR (เช่น 2.0.0):** การเปลี่ยนแปลงสถาปัตยกรรมหลักที่มีผลกระทบต่อโครงสร้างฐานข้อมูล หรือการเปลี่ยนวิธีเชื่อมต่อ API

### 4.2 ขั้นตอนการทดสอบและปล่อยอัปเดต (Release Workflow)
1. ดำเนินการแก้ไขและทดสอบบนเครื่องจำลอง (Local/Staging)
2. รันชุดทดสอบอัตโนมัติเพื่อยืนยันว่าไม่มีผลกระทบข้างเคียง (Regression Testing):
   ```bash
   python -m unittest test_integration.py
   ```
3. เมื่อการทดสอบผ่าน 100% จึงดำเนินการอัปเดตไฟล์ขึ้นเซิร์ฟเวอร์จริงนอกเวลาทำการราชการ (ช่วงเวลา 19:00 - 21:00 น.) พร้อมแจ้งเตือนผู้ใช้งานล่วงหน้าอย่างน้อย 24 ชั่วโมง
